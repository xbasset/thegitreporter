Claude API Gateways Can Now See Customer Restrictions

If your app gives many customers access to Claude through one account, you can now look up which customer profile Anthropic has restricted. The new API fields help operators investigate a disruption; they do not guarantee that everyone else stays online.

Anthropic added customer restriction fields to the Claude API in its October 20–21 releases. A gateway—the service forwarding an app’s customer requests through a shared Claude account—can now look up the restrictions or bans reported for each profile. The fields are present in the released anthropics/anthropic-sdk-python v2.1.0.

The practical gain is a more precise investigation: an operator can look up the affected customer’s record instead of treating every failure as a shared-account problem. Anthropic says attribution can allow action against one customer while other traffic continues. The public interface exposes the record; it does not establish how reliably that isolation works.

The AWS exception

On Claude Platform on AWS, these fields remain unrestricted and empty: they do not report open actions, and those actions do not cause refusals there. An empty response is not a clearance signal.

Read the platform-specific contract. This is an account-to-record explanation, not a simulation of enforcement.

The new part is the view into enforcement

Profiles already existed in the earlier beta SDK. The October 20 general release was followed the next day by status, action details and a filter for listing affected profiles. This is a released client interface around an existing attribution system, rather than evidence that targeted enforcement began this week.

A profile is a record for someone the platform serves. It can identify a user of an application or a company buying resold access. The response model keeps the platform’s supplied customer details distinct from Anthropic’s enforcement fields. That gives operators two different facts to reconcile: their own account decision and the provider’s current restriction.

A status page needs more than a timestamp

The SDK exposes a practical trap for anyone building that view: updated_at does not reliably advance when reported status changes. Read the status itself. The same response definition includes pending for a qualified identity-check review condition, beyond the three principal states described in the overview. A fixed green/amber/red legend would miss part of the contract.

The filter’s pagination rules matter too. A page can contain no matching profiles and still supply a continuation cursor. Stopping at that empty page can leave affected customers undiscovered. The listing is finished only when next_page is null. Keeping an old profile beta header also leaves out the new fields or rejects the filter.

Organization webhooks offer another route to updates, but remain a beta requiring access from Anthropic’s account team. An event carries identifiers; the consumer retrieves the profile to learn its current state. Delivery can be delayed or out of order, so the latest arriving notification is not necessarily the latest condition.

What an operator can now establish

The client implementation constructs the profile requests and forwards the filter. Its generated tests check methods and response shapes against a configurable test endpoint. We inspected these sources; we did not run the suite or trigger a live restriction. They do not measure classifier quality, reduced collateral bans or uninterrupted service for another customer.

The next useful demonstration is a public gateway integration on a specified platform: customer IDs survive the request path, the operator reconstructs current status after missed notifications, and recovery reaches the right account. The gain this week is concrete. A shared service has a released interface for asking whose restriction it is dealing with—and a clearer contract for interpreting the answer.

Evidence Limits

  • Interface inspection, not a live enforcement trial. SDK tests were not run.
  • No measurements of classifier quality, collateral bans, adoption or continuity of unaffected production traffic.
  • Visual records are hypothetical, not an actual restriction or an exhaustive status machine.
  • Platform contracts differ; unrestricted/empty on Claude Platform on AWS does not establish absence of open actions elsewhere.
  • Private service classification and enforcement cannot be audited through client code.
