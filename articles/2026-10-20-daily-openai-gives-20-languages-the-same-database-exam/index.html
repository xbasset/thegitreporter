OpenAI Gives 20 Languages the Same Database Exam

MultiLangBench asks a model to build a database engine in a chosen language. The revealing part is the examiner: reference SQLite reads the file that implementation leaves behind.

In a report published October 19, OpenAI presents the public openai/MultiLangBench suite alongside its claim of stronger coding in less common languages. It reports an average test pass rate of 87.4% for GPT-6 Astra across 20 languages, compared with GPT-5.6 Sol's 26.8%. The accompanying public suite lets readers inspect what those percentages are trying to measure.

The shared contract

The language changes.
The examiner stays outside.

A candidate program receives an existing database and a SQL request. It must leave a modified database that the real SQLite implementation can read. The test checks a specified query against that file. Printing a convincing answer is insufficient.

This is a useful way to compare implementations written in languages with very different tools and conventions. The interface is a common artifact, rather than language-specific unit tests. The published contract requires the chosen implementation language and an offline environment stripped of existing SQLite implementations.

What passes through the file

Selection is only half the answer.
The rows have to survive.

In this example, the implementation needs to understand a request, find three matching pairs, put them in the requested order and write a table the reference reader can recover. The check crosses the boundary between the candidate's internal representation and a persistent database file.

The golden-output generator makes that boundary inspectable. It pins SQLite 3.40.1, builds the starting database and produces the reference result. It then opens the output read-only and serializes the validation query's rows. That script establishes expected answers; it does not run a coding model.

Read the denominator

A common exam.
A bounded slice of behavior.

The repository describes roughly 24,000 converted SQLite tests and recommends a 272-test subset for routine evaluation. A passing case establishes the answer to its validation query. It cannot establish every database behavior, execution plan or performance property.

The gain reported by OpenAI is substantial, including in COBOL, its hardest language in this comparison. But these are the provider's measurements. We inspected the contract, fixture, scripts and history; we did not reproduce model scores. The repository contains no candidate implementations or complete agent-run records that would independently establish them.

The strongest competing reading is therefore specific: models may have become much better at this database-construction task without improving equally on every unfamiliar business system. The useful next experiment is to make that distinction observable.

Building an engine and migrating a system are different exams

OpenAI separately reports COBOL migration results using GPT-6.1 Sol and hidden tests of output equivalence. Those results do not come from this public database suite. A team's existing rounding rules, record formats and dependencies require their own checks.

Source history and inspection limits

The methodology is present in the September 29 initial commit. The October 19 change renames the project. Commit dates do not establish when it first became public. Today's news is the announcement and public test offering, not newly changed test logic. No agent run, reference-suite execution or production migration was performed for this article.

For a team choosing a coding model, the release offers something practical: inspect the shared tests, then ask whether their demands resemble the work you need a model to do in your language. A reproducible run with published code, task budget and per-test outcomes would turn the reported score into a comparison others can examine. The database file gives them a common place to start.

Evidence Limits

  • No model run, score reproduction, timing measurement or production migration was performed.
  • Scores are OpenAI-reported. The inspected repository contains no candidate implementations, complete execution records or result tables establishing them independently.
  • A validation query observes selected behavior, not every SQLite feature, performance property or legacy business rule.
  • The separate COBOL migration evaluation uses hidden tests and a different model; this database-construction suite does not reproduce it.
  • Commit dates do not establish when the repository first became public.
