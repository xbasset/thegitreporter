Audit whether an agent workflow leaves a restart-safe review record

Qwen Code's merged workflow-state change records terminal lifecycle events, phase visits, dispatch dependencies, retry lineage, and a reconstructed snapshot. Builders of multi-agent workflows should audit whether their own restart path preserves that topology, not merely logs and final text, before trusting an operator to decide what can be rerun after a process dies.

Today's Action

Audit / Project-specific claim
action

Audit whether an agent workflow leaves a restart-safe review record

What changed. PR #9034 adds a structured runtime model for workflow execution. The persisted snapshot projects terminal registry state into a JSON record that includes source-run lineage, phase visits, dispatch traces and dependencies, events, logs, token accounting, result, and error state; `/workflows` can rebuild a terminal task from that snapshot after the CLI restart boundary.

Why it matters. A workflow's final output cannot on its own say which branch ran, which predecessor a retry came from, or whether a missing result is a cancellation, a failure, or an unfinished dispatch. The recommended audit is a bounded design and failure-path exercise, not a claim that a released Qwen Code build or every agent runtime has this behavior.

Claim coverage / complete 27 / 27

All 27 included projects and all 13 core coding agents have fresh source receipts for this edition.

Builder or operator responsible for a multi-agent workflow that may be restarted or retried 30–60 minutes for a disposable run and persistence-path inspection

Inspect one terminal workflow record after a controlled restart

In a disposable workflow with harmless tools, complete or deliberately cancel a run that has at least two phases and one dependent subagent dispatch. Restart the host process, then inspect the persisted record. Verify that it identifies the prior run, phase visits, dispatch order or dependencies, terminal state, and error or result without inferring those facts from an unstructured log. Record any effect whose completion would still be uncertain before allowing an automatic retry.

Confidence / developing

A fresh public merge, its public PR description, and the pinned snapshot implementation agree on one narrow restart-boundary mechanism. The recommended audit is deliberately limited to a disposable workflow and does not depend on release availability.

Limit

These public main-branch sources and tests do not establish that a released Qwen Code build exposes the workflow surface, that every snapshot write succeeds, that an active run remains inspectable after a crash, or that another runtime shares its persistence model.

What would change this

Revise or withdraw this call if a public end-to-end restart path demonstrates that phase, dispatch, and lineage data are not actually reconstructed for a completed or cancelled workflow, or if the stored record cannot distinguish a retry's predecessor from a new run.

Watch next. Watch for release documentation and a public restart reproduction that exercises an interrupted dependent dispatch, shows what remains uncertain about an external effect, and names the supported recovery choice.
