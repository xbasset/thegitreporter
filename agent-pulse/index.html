Today's Action

watch

Watch where an OpenWork Cloud client refreshes its runtime address

What changed. OpenWork's public refactor deletes its standalone den-worker-proxy and moves Cloud runtime resolution into a shared worker-access path. The focused evaluation refreshes an expired signed preview, preserves a stable API route for a legacy client, resolves that route to the current preview before forwarding, and rejects a sandbox-controlled health-check redirect.

Why it matters. An expiring runtime URL and a stable client endpoint answer different operational needs. Treating their handoff as one visible resolution boundary can make a Cloud connection easier to reason about, but the evidence remains public main-branch source and tests rather than release, default-configuration or deployment proof.

Operator or maintainer evaluating an OpenWork Cloud build that uses signed runtime previews 15–30 minutes in a disposable Cloud workspace

Trace one harmless refresh through the connection boundary

In a disposable Cloud workspace, observe one normal connection and one harmless reconnect after the preview is renewed. Record whether a stable client route resolves the fresh destination at request time, whether an expiring direct preview is not retained as the durable address, and whether an unexpected redirect or unavailable preview fails safely. Do not use this as a credential, security or release-availability test.

Confidence / developing

The merged public commit, its shared access implementation and its deterministic runtime evaluation agree on the intended split between a stable client route and an expiring signed preview. The call remains a watch because the evidence does not establish a release, default enablement or behavior in a particular Cloud deployment.

Limit

The receipts do not establish that a released OpenWork build contains the refactor, that signed previews are enabled in every environment, that the behavior performs consistently under load, or that the focused redirect check covers every authentication and network failure path.

What would change this

Revise or withdraw the call if public source or a regression shows a legacy stable route retaining a stale preview host, bypassing access resolution when a preview expires, following a sandbox-controlled redirect, or a released contract that materially changes the client-routing model.

Watch next. Watch for release documentation that specifies preview expiry, stable-client compatibility and user-visible failure behavior, plus public regression tests for renewed credentials and unavailable previews.
