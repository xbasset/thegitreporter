Audit whether an agent Hub can retire without replaying work as a second action

Cline's merged Hub change adds a drain-before-upgrade path, durable event replay, and event-id deduplication for reconnecting clients. Operators of durable agent services should audit one non-production replacement boundary: whether it stops admitting new mutable work, distinguishes accepted work from safely terminal work, and lets a reconnect catch up without treating a replayed event as a new instruction.

Today's Action

Audit / Project-specific claim
action

Audit whether an agent Hub can retire without replaying work as a second action

What changed. PR #13468 adds `cline hub drain` and an upgrade sequence that requests a drain, checks idleness, stops an idle Hub, and starts a replacement; an abort path un-drains the existing Hub. The same merge persists Hub events, replays events after a sequence cursor, buffers live events during replay, and deduplicates the same logical event by stable `eventId` rather than only by a durable sequence applied later.

Why it matters. A durable agent service has more state than a process: accepted sessions, event consumers, and potentially pending decisions can cross a replacement boundary. The proposed audit is a reversible staging exercise. It is not a claim that Cline has released the commands, that any production upgrade completed, or that a drained Hub proves every external side effect is safe to abandon.

Claim coverage / complete 27 / 27

All 27 included projects and all 13 core coding agents have fresh source receipts for this edition.

Operator or platform engineer responsible for an agent service that retains sessions, streams events, or accepts background work 30–60 minutes in a staging or disposable environment

Rehearse one drain and reconnect path with harmless work

In a disposable environment, start a harmless long-running agent task and attach a client that records stable event identifiers. Request a drain, attempt one new mutating request and confirm it is refused, allow the accepted task to reach its documented idle or terminal boundary, replace the service, reconnect from an earlier cursor, and verify that replayed events are identified as prior events rather than submitted again as new actions. If any external effect remains uncertain, record it as uncertain instead of inferring completion from the process restart.

Confidence / developing

The fresh public merge, CLI command tests, and replay adapter agree on one bounded replacement mechanism. The recommendation stays inside a disposable audit and does not rely on a release or production-success claim.

Limit

The receipts are public main-branch source and focused tests. They do not establish release availability, an executed production replacement, exactly which external tool effects a Hub considers complete, or whether every client uses the replay protocol correctly.

What would change this

Revise or withdraw the call if a public replacement path admits new mutations after drain, leaves an aborted upgrade permanently drained, delivers the same durable logical event twice after replay, or shows that the idle check treats an unresolved external action as safely terminal.

Watch next. Watch for a release-backed integration test that replaces a live Hub during a reconnect and a durable run, while exposing the documented boundary for pending approvals and externally owned effects.
