Agent Pulse / Daily decision brief / 2026-08-20

Audit workspace binding before letting an agent schedule recurring work

Cline's public main-branch task-and-schedule change makes an agent-created recurring job a durable workspace object rather than just a deferred prompt. Builders who are adding agent schedules should audit whether their own scheduler takes workspace identity and connected-client authority from trusted session state, rather than from a mutable task request or the process that happens to execute it later.

One decision-worthy insight. Action, effort, and rollback. 27 / 27 included projects monitored. Methodology ›

Today's Action

Audit / Project-specific claim
action

Audit workspace binding before letting an agent schedule recurring work

What changed. Cline's schedule tool requires a Hub session, canonicalizes the session's workspace and working directory, uses them when it creates a schedule, and rejects later schedule records outside that scope. The matching Hub task command service derives a workspace from connection authority, ignores a spoofed creator in a create payload, and rejects access outside that workspace; the vertical-slice test rejects an unregistered schedule client before a registered workspace client can list the schedule.

Why it matters. A recurring agent job retains its effects after the turn that created it. If its workspace or actor can drift between creation, review, execution, and cancellation, a useful reminder surface can become an authority handoff. The bounded action is an audit of a disposable multi-workspace path, not a claim that Cline has released the feature or that every scheduler shares this design.

Claim coverage / complete 27 / 27

Builder or operator running agent-created tasks across more than one repository 30–60 minutes for a two-workspace reproduction and identity-path inspection

Attempt a cross-workspace schedule operation in a disposable harness

Create two disposable workspaces with no credentials or production files. Create one harmless scheduled task from the first workspace, then connect through the second and attempt to list, update, trigger, or cancel it. Verify from redacted diagnostics that the operation is rejected unless the client and task share trusted workspace identity; also confirm that request-supplied creator or workspace fields cannot override the connection boundary.

Confidence / developing

A fresh public merged commit, the scope-enforcing implementation, authenticated Hub command boundary, and focused vertical-slice tests agree on one narrow workspace-identity contract. The recommendation is a disposable audit, not a statement about release availability or the safety of every execution mode.

Limit

The receipts are public main-branch code and tests. They do not establish that a released Cline build exposes this surface, how a particular provider or extension executes a task, how often cross-workspace attempts occur, or that another agent scheduler uses the same trust boundary.

What would change this

Revise or withdraw this call if a public released-path reproduction shows that an authenticated client can list, mutate, trigger, or cancel a schedule in a different workspace without a separately authorized global scope, or if the schedule path takes its authoritative workspace from mutable tool input rather than the resolved session connection.

Watch next. Watch for release documentation that names the schedule execution modes and their approval behavior, plus a public two-workspace integration test that exercises creation, execution, update, and cancellation through the supported client surfaces.
