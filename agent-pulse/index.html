Audit what a remembered approval still remembers

Codex's public main-branch changes narrow three ways approval reuse can drift: a parent grant can conceal an explicitly denied child path, a trusted-looking inner command can conceal an unfamiliar shell executable, and a cached Guardian review score can lag the newest tool call. Builders with reusable agent approvals should audit the narrowest exception and executable identity in a disposable policy test instead of treating a remembered yes as a broad, durable capability.

One decision-worthy insight. Action, effort, and rollback. 27 / 27 included projects monitored. Methodology ›

Today's Action

Audit / Project-specific claim
action

Audit what a remembered approval still remembers

What changed. Codex now materializes permission profiles before calling a request preapproved and runs an accepted replay with the stored grant so its denied paths remain enforced. Its Unified Exec path evaluates an unfamiliar shell executable alongside parsed commands and includes the executable in reusable approval keys. Guardian v2 additionally records tool-call score lag and a `score_lag` fallback counter when a cached review score exceeds the configured freshness limit.

Why it matters. Approval reuse is a convenience boundary, not a durable statement that every related action is trusted. An exception that disappears during profile comparison or a cache key that omits the executable can turn a narrow decision into authority for a different target. Measuring stale review state is useful, but it should not be mistaken for a decision or a release guarantee.

Claim coverage / complete 27 / 27

All 27 included projects and all 13 core coding agents have fresh source receipts for this edition.

Builder or operator maintaining a reusable approval cache for an agent harness 30–60 minutes for a disposable harness test and approval-cache inspection

Exercise the narrowest denial and a swapped executable in a disposable policy test

In a disposable repository with no credentials or customer files, grant a harmless workspace write while explicitly denying one child directory. Request a read and a write beneath that child through every relevant tool route and confirm that each needs a new decision. Then repeat one otherwise-identical safe command through two distinct test shell wrappers and verify that an approval for one wrapper cannot authorize the other. Preserve only redacted logs; do not test against production files or broad filesystem permissions.

Confidence / developing

Three fresh public Codex commits and their focused tests agree on narrow approval-reuse mechanics. The action is a disposable audit of a reader's own policy semantics, not a claim that a release is installed, that the observed cases are common, or that telemetry determines live safety outcomes.

Limit

The receipts are main-branch source and tests. They do not establish release availability, production telemetry, the frequency of an approval-edge case, the behavior of another agent framework, or the final decision made by any live Guardian review.

What would change this

Revise this call if public tests or a released-path reproduction show that a denied child remains protected even when an equivalent profile comparison omits the deny, or that a reusable approval key already includes an unfamiliar executable without relying on its parsed inner command. Narrow the freshness claim if public code shows the `score_lag` counter is not attached to the approval-review path described here.

Watch next. Watch for a release receipt and a public, scoped explanation of how stale Guardian scores reach user-visible approval behavior; then rerun the disposable nested-denial and swapped-executable checks against that released path.
