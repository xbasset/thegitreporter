Audit whether a frozen release still knows which workflow may publish it

OpenClaw's merged release-tooling change keeps the product's Code SHA/ref separate from the Tooling SHA/ref and, for its covered npm publication route, rechecks an exact protected tag and release-publish parent run immediately before a registry mutation. Builders who maintain release automation should audit whether their own pipeline can distinguish the reviewed workflow revision from a later-moving branch, rather than treating a ref name or old approval as a durable publishing identity.

Today's Action

Audit / Project-specific claim
action

Audit whether a frozen release still knows which workflow may publish it

What changed. PR #126881 adds an identity verifier that accepts the protected route only as the exact lightweight `release-publish/<sha>-<run>` tag and matching workflow SHA. It reads the live remote tag reference, rejects a missing, moved, annotated, wrong-SHA, or same-name-branch substitute, and validates the repository, workflow path, head SHA, run ID, run attempt, and allowed state of the release-publish parent run before the covered npm paths proceed.

Why it matters. Release validation and release mutation are separated by time and often by unrelated repository activity. If the workflow identity can silently refresh from a moving branch, a reviewed candidate can reach a privileged writer under different rules. The recommended audit is a dry-run or source-level check of one pipeline boundary; it is not a claim that OpenClaw has shipped a package under this control or that every publisher is covered.

Claim coverage / complete 27 / 27

All 27 included projects and all 13 core coding agents have fresh source receipts for this edition.

Release engineer or maintainer responsible for a CI path that validates and then publishes a package or artifact 30–60 minutes for a dry-run workflow or source-level verifier test

Try identity substitution in a non-publishing release rehearsal

In a disposable repository or a CI dry-run that cannot write a registry, freeze a candidate commit and its workflow revision. Before the final simulated publish step, attempt four substitutions: move or delete the protected tag, replace it with an annotated tag, use a same-name branch, and supply a different approval run or attempt. Confirm from redacted logs that each is rejected and that the normal moving-branch route is not silently used as a fallback.

Limit

The receipts are public main-branch source, PR text, documentation, and focused tests. They do not establish that any OpenClaw package has been published under the route, that every privileged writer is protected, that a release has completed successfully after main advanced, or that another CI system has the same behavior.

What would change this

Revise or withdraw this call if a public covered publish path accepts a moved tag, an annotated tag, a same-name branch, or a mismatched parent run; narrow it if the released workflow no longer reads the live protected-tag identity immediately before the npm mutation.

Watch next. Watch for the dependent writer changes and a public release receipt that carries a frozen tooling identity through the covered npm route after main advances, while still rejecting substituted identities.
