Audit which configuration layer gets to broker a Codex credential

If you are evaluating a Codex main-branch build that includes its new network-proxy credential broker, audit the configuration layers before enabling it: a project configuration should not be able to select the broker or replace its provider context, while a trusted layer should have a deliberate policy for sandboxed and escalated commands.

Today's Action

Audit / Project-specific claim
action

Audit which configuration layer gets to broker a Codex credential

What changed. The fresh public Codex commit adds a credential-broker setting, sanitizes broker and provider-context values out of project configuration when trusted broker configuration exists, carries trusted context into filtered shell environments, and restores brokered credentials in the explicit unsandboxed escalation path. Its end-to-end zsh-fork test checks that the real fixture GitHub token does not appear in sandboxed output.

Why it matters. A repository is a collaborative work surface, while credential policy is a trust decision. Separating them can make an agent workflow easier to reason about, but the source is implementation and tests rather than a release guarantee or evidence that every provider and deployment shares the boundary.

Trace the credential decision across configuration layers

In a disposable test setup, map the user, managed, thread, and project configuration layers that can reach Codex. Verify that project-controlled configuration cannot enable the broker or replace provider-context variables, then run one harmless sandboxed command and one separately approved escalation-path check without placing a real secret in repository files.

Limit

The receipts do not establish that the feature is released or enabled by default, that a given Codex installation includes it, or that every credential provider, operating system, shell, extension, and escalation path has equivalent protection.

What would change this

Revise or withdraw this call if public configuration documentation or a regression shows that project files can still enable the broker or replace trusted provider context, that a sandboxed command receives the real test credential, or that the escalation path restores credentials outside its explicit trust transition.

Watch next. Watch for released configuration guidance that names supported broker providers, configuration precedence, and observable behavior for sandboxed versus escalated commands.
