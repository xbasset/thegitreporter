Agent Pulse / Daily decision brief / 2026-08-12

Audit whether a shared agent is silently using one operator identity

OpenClaw’s fresh per-requester OAuth work supports one bounded audit for teams that place an agent in a trusted shared channel: identify every connected HTTP MCP service and decide whether its credentials should belong to the operator or to each sender. The public source adds an opt-in requester identity that gives each sender a separate OAuth flow and credential scope instead of treating the shared room as proof that one account is appropriate for every tool call.

One decision-worthy insight. Action, effort, and rollback. 26 / 26 included projects monitored. Methodology ›

Today's Action

Audit / Project-specific claim
action

Audit whether a shared agent is silently using one operator identity

What changed. The public implementation introduces `oauth.identity: "per-requester"` for HTTP MCP OAuth, scopes requester credentials by channel, agent account, and sender, and completes the sender’s authorization through the Gateway callback at `/oauth/mcp/callback`. The guide says an unauthenticated sender gets a sign-in link and retries the tool after connecting; static and scheduled runtimes are excluded because they have no requester identity. The focused source receipt includes a two-user self-hosted gateway end-to-end path.

Why it matters. A shared agent can be a convenient common interface without making a shared credential the hidden authority behind every request. Naming the credential owner gives operators a testable boundary before a room that mixes people, roles, or accounts acquires access to a personal system.

Claim coverage / complete 26 / 26

All 26 included projects and all 13 core coding agents have fresh source receipts for this edition.

Operator of an OpenClaw agent in a trusted shared channel with connected HTTP MCP services 20–30 minutes

Map one service’s credential owner

In a disposable test channel with non-sensitive data, list one connected HTTP MCP service and identify whether the current configuration uses one operator-managed OAuth credential or a requester-specific one. If per-requester identity is appropriate, verify that the Gateway has a reachable HTTPS publicOrigin, connect two test senders to distinct disposable accounts, and confirm each tool call uses only its sender’s account. Treat sign-in links as bearer links; do not test this in a channel whose participants are not mutually trusted.

Confidence / developing

A fresh public implementation receipt, the public configuration reference, and focused test claims agree on the narrow credential-ownership mechanism, but the evidence is main-branch source and documentation rather than a release or production observation.

Limit

These receipts show intended source behavior and documentation. They do not establish a released build, independent security review, production deployment, private delivery of sign-in links, or a complete channel-membership authorization system.

What would change this

Revise this call if a public regression shows that two requesters can receive the same stored credential under the configured mode, a per-requester server runs without a sender identity in a static or scheduled path, the callback accepts stale or mismatched state, or the documentation changes the trusted-channel boundary materially.

Watch next. Watch for a release note, public adversarial tests around link handoff and changing channel membership, and a requester-private authorization handoff that would narrow the guide’s current bearer-link caveat.
