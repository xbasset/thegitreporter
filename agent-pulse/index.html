Audit whether a coding agent’s “completed” state carries a file-delta receipt

Cline’s fresh checkpoint work supports one bounded audit for teams that accept coding-agent completion messages: ask whether the interface gives a reviewer the exact files changed since the user’s last instruction, rather than only a prose summary. The inspected implementation restores that comparison in the completion card and its follow-up makes the control unavailable when the host finds no changed files in the defined interval.

Today's Action

Audit / Project-specific claim
action

Audit whether a coding agent’s “completed” state carries a file-delta receipt

What changed. The public Cline source takes a checkpoint when the user’s last message starts a run, opens a multi-file diff from that point to the current working tree, and adds a separate latest-change count that keeps the completion-row control faded and disabled unless files actually changed. This creates a source-visible receipt boundary without turning the UI into a claim that the work is semantically correct.

Why it matters. A completion message can be useful narration, but it is not enough evidence for a reviewer deciding whether to accept an agent’s work. A bounded changed-file receipt makes the first review question cheap and explicit: inspect the delta before treating the agent’s final answer as done.

Claim coverage / complete 26 / 26

All 26 included projects and all 13 core coding agents have fresh source receipts for this edition.

Builder or operator who accepts coding-agent changes in a shared repository 15–20 minutes

Trace one completion-to-diff path

In a disposable clone with no production credentials, ask your coding agent to make one harmless, reversible change. At completion, identify the exact baseline used for its file diff, confirm that the UI distinguishes a zero-change turn from a changed-file turn, and inspect the delta before accepting the result. Do not use the drill to bypass an existing review or approval process.

Confidence / strong

Two fresh public Cline commits, directly inspected UI and checkpoint paths, and focused tests agree on the narrow completion-to-diff mechanism and its no-change guard.

Limit

These public source and test receipts show intended main-branch behavior. They do not establish a released extension, semantic correctness of an agent task, coverage of every workspace state, or a complete security and review process.

What would change this

Revise this call if a public regression shows that the completion-row diff uses an unrelated baseline, includes no-change turns as changed work, omits a named file class from the documented interval, or exposes the action without the host confirmation described in the source.

Watch next. Watch for public end-to-end checkpoint tests that cover untracked files, renames, conflicts, and external workspace changes; those cases will show how durable the receipt boundary is beyond the focused source path.
