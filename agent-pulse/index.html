Audit repository startup settings before trusting a Gemini CLI workspace

If you run Gemini CLI's A2A server against projects you did not author, audit one restricted-workspace start: verify that repository-defined MCP servers, policy paths, tool settings and telemetry are absent until an explicit trust decision is made.

One decision-worthy insight. Action, effort, and rollback. 29 / 29 included projects monitored. Methodology ›

Today's Action

Audit / Project-specific claim
action

Audit repository startup settings before trusting a Gemini CLI workspace

What changed. Gemini CLI's merged public workspace-trust change gives explicit restricted-mode or untrusted environment signals precedence and, when the A2A server is untrusted, passes a filtered configuration view that omits repository-defined MCP servers, policies, admin policies, tools and telemetry.

Why it matters. A checkout can describe more than source code when it configures an agent runtime. Separating the trust decision from the configuration that would start tools or route telemetry makes the authority boundary testable before an operator gives a project more access.

Claim coverage / complete 29 / 29

All 29 included projects and all 13 core coding agents have fresh source receipts for this edition.

Maintainer or operator evaluating a Gemini CLI A2A workspace from an unfamiliar repository 20-40 minutes in a disposable test workspace

Trace one restricted startup configuration

In a disposable environment, start the A2A path with an explicit restricted or untrusted workspace signal and a harmless repository settings fixture. Verify that MCP server, policy, admin-policy, tool and telemetry settings are not active before an explicit trust decision. Do not use the exercise as a claim that every Gemini CLI entry point or operating-system policy has been audited.

Evidence Chain

Receipt 1 / google-gemini/gemini-cli / commit / Aug 28, 11:38 PM GMT+2 Enforce fail-closed workspace trust and filter MCP servers in restricted mode

Shows the merged main-branch trust-resolution and A2A configuration change that filters repository-defined MCP servers, policy paths, admin-policy paths, tool settings and telemetry when the workspace is untrusted.

 Receipt 2 / google-gemini/gemini-cli / runtime-test / 2026-08-28T21:38:20Z A2A workspace trust evaluation test

Shows focused public tests for restricted environment signals and for the absence of the sensitive configuration families when the A2A loader receives an untrusted workspace.

Confidence / developing

The merged commit, pull-request description and focused workspace-trust tests agree on the intended A2A configuration boundary. The evidence is source and test material, so the action remains an audit rather than a claim about a released build or every runtime path.

Limit

The receipts do not establish that a released Gemini CLI build includes this change, that every command or extension startup route shares the filter, or that the named controls exhaust the configuration and security surface of a workspace.

What would change this

Revise or withdraw the call if public source or regression tests show a restricted A2A workspace activating a repository-defined MCP server, policy, admin policy, tool setting or telemetry route before an explicit trust decision, or if documented behavior materially narrows the filter.

Watch next. Watch for release documentation and cross-entry-point tests that specify restricted-mode behavior beyond the A2A loader, especially for extension discovery and new repository-controlled configuration families.
