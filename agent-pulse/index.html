Audit whether a refreshed Codex cloud configuration applies to your current session

Codex's fresh cloud-configuration change supports a narrow audit for teams that rely on managed configuration: do not assume a background refresh changes an already-running session. The inspected source says the old path warmed disk while new sessions in the same process retained the startup snapshot; the proposed implementation reloads the shared bundle for later configuration loads and keeps the last successful bundle when a refresh fails.

Today's Action

Audit / Project-specific claim
action

Audit whether a refreshed Codex cloud configuration applies to your current session

What changed. The public change makes CloudConfigBundleLoader retrieve the latest shared bundle on each configuration load, updates the in-memory bundle only after a successful refresh, and cancels refresh work when its loader is replaced or its final clone is dropped. Its focused tests cover refreshed requirements and managed configuration in later sessions, concurrent initial loads, failure and recovery, clearing, and refresh-task cancellation.

Why it matters. Configuration controls can look live while a long-running agent process is still acting on an earlier policy bundle. Knowing the session boundary lets an operator verify a sensitive change deliberately instead of assuming a background fetch changed the next tool decision in place.

Claim coverage / complete 26 / 26

All 26 included projects and all 13 core coding agents have fresh source receipts for this edition.

Operator responsible for managed Codex configuration 15–30 minutes

Test the session boundary in a disposable environment

In a disposable managed configuration environment, make one harmless configuration change, allow the documented refresh path to run, then compare one already-running session with a newly started session. Record which session sees the revised requirement and keep existing approval or review controls in place; do not use the test to weaken a policy boundary.

Limit

The commit and tests show intended source behavior, not a released deployment, the exact refresh cadence of a managed environment, or behavior across every client, cache, and policy configuration.

What would change this

Revise this call if a public regression shows that an already-running session receives the refreshed bundle through a different path, a later session still retains the startup snapshot after a successful refresh, or the change is reverted or materially redesigned.

Watch next. Watch for release documentation or public integration coverage that names the configuration-refresh boundary and verifies it against a running managed session; that would determine how directly operators can rely on this source change.
