Audit the required-compaction path before trusting an oversized Codex session

OpenClaw’s public issue and main-branch fix show a specific failure mode in which a required reply preflight accepted neither an intentional Codex app-server no-op nor a real compaction, then dropped the incoming turn. Operators using Codex app-server sessions should audit the installed version and a disposable budget-crossing path before assuming automatic compaction preserves the next message.

One decision-worthy insight. Action, effort, and rollback. 27 / 27 included projects monitored. Methodology ›

Today's Action

Audit / Project-specific claim
action

Audit the required-compaction path before trusting an oversized Codex session

What changed. The issue traces a required preflight that received `ok: true, compacted: false` because the Codex app server owned automatic compaction, but the reply path classified that result as fatal. The follow-up change labels the request `required_preflight`, dispatches native compaction, and converts only missing or stale Codex bindings into an explicit recoverable failure for the existing context-engine fallback.

Why it matters. The useful distinction is between a benign status and a completed recovery. If a system says compaction is required, accepting an uncompacted no-op can silently turn a context-management contract into lost user input. A bounded audit is safer than treating a main-branch repair as proof that all long-context sessions are reliable.

Claim coverage / complete 27 / 27

All 27 included projects and all 13 core coding agents have fresh source receipts for this edition.

Operator or builder running OpenClaw with a Codex app-server harness 15 minutes to identify the build and plan the test; 30–60 minutes for a disposable reproduction

Check the required-preflight handoff in a disposable session

First identify whether the installed build contains the public required-preflight change. In a non-production session with no sensitive conversation state, cross the configured context budget once and verify that the next user turn reaches a model reply or produces a documented recoverable binding path. Preserve only redacted diagnostics; do not force compaction against a live customer or production session as this test.

Confidence / developing

A fresh public issue, implementation change, and focused tests agree on one narrowly scoped Codex app-server failure and recovery contract. The action is an audit of a disposable path, not a claim that a release or every deployment has the repair.

Limit

These are public issue, main-branch code, and test receipts. They do not establish an installed release, frequency across deployments, behavior for non-Codex harnesses, or safety of forcing compaction on a live conversation.

What would change this

Revise or withdraw this call if a public released-path reproduction shows that the required-preflight route still drops an otherwise valid user turn after native compaction succeeds, or if the stated fallback allows a stale binding to bypass the existing context-engine recovery boundary.

Watch next. Watch for a release note naming the patch and for an independent operator report that exercises the same required-preflight path with a real Codex app-server session and a redacted before-and-after outcome.
