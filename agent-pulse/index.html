Audit whether scheduled OpenWork jobs have an explicit workspace target

If your OpenWork setup has Automations created before workspace pinning, audit one recurring job: verify whether it records a workspace ID and, if the intended workspace is unavailable, fails visibly rather than running in whichever workspace is currently active.

Today's Action

Audit / Project-specific claim
action

Audit whether scheduled OpenWork jobs have an explicit workspace target

What changed. OpenWork's public main-branch workspace-pinning change carries an optional workspace ID from Automation creation into the desktop runner and cloud executor. The desktop runner selects a present pin and raises an unavailable-runtime error for a missing one; older unpinned assignments keep the active-workspace fallback.

Why it matters. A scheduled agent is an execution commitment, not a continuation of a person's current navigation state. Making its target explicit lets an operator audit where work will occur and turns a silent retarget into a recoverable, visible failure.

Claim coverage / complete 29 / 29

All 29 included projects and all 13 core coding agents have fresh source receipts for this edition.

OpenWork maintainer or operator who schedules Automations across more than one workspace 20-30 minutes in a disposable or non-production workspace

Trace one Automation's workspace identity

In a disposable or non-production workspace, create or inspect one Automation and verify that its revision records the intended workspace. Then make that workspace unavailable and confirm the runner reports an unavailable runtime rather than selecting the active workspace. Treat old assignments without a pin as a migration/audit finding, not as evidence that every runner path is protected.

 Receipt 2 / different-ai/openwork / runtime-test / 2026-08-29T14:45:44Z Desktop Automation workspace-selection regression tests

Shows focused public witnesses that a pinned workspace wins over the active workspace and that a missing pin fails rather than silently retargeting the job.

Confidence / developing

The public commit narrative, implementation and focused desktop-runner tests agree on the intended placement behavior. The evidence is source and test material, so the action is an audit rather than a claim about a released build or every execution surface.

Limit

The receipts do not establish that a released OpenWork build contains the change, that all existing Automations have a workspace pin, or that desktop and cloud recovery behavior has been independently verified in a production deployment.

What would change this

Revise or withdraw the call if public source or regression tests show a present but unavailable workspace pin being replaced by the currently active workspace, or if documented behavior says the pin is not carried to an execution path the article names.

Watch next. Watch for release and migration guidance that lets operators identify legacy unpinned Automations and for end-to-end receipts covering cloud recovery after the target workspace changes.
