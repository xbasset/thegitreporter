Audit who owns the HTTP cookie jar beneath your agent sessions

Microsoft Agent Framework’s September 15 Python change rejects response-cookie persistence in internally created HTTP clients. Before adopting it, identify which integrations rely on cookies and which authenticated users share caller-owned clients.

One decision-worthy insight. Action, effort, and rollback. 29 / 29 included projects monitored. Methodology ›

Today's Action

Audit / Project-specific claim
action

Audit who owns the HTTP cookie jar beneath your agent sessions

What changed. Framework-created MCP, A2A, AG-UI and declarative HTTP clients use a cookie policy with no allowed domains. Connection reuse remains; supplied clients and explicit cookies retain their behavior. Separate agent sessions do not by themselves partition transport or server-side identity.

Why it matters. A shared cookie jar can carry one run’s authentication into another, while removing persistence can break legitimate same-session authentication or affinity. The migration requires an explicit ownership decision.

Claim coverage / complete 29 / 29

All 29 included projects and all 13 core coding agents have fresh source receipts for this edition.

Teams using Microsoft Agent Framework’s Python HTTP integrations 20–30 minutes for one existing integration

Trace one client across two test users

In a disposable integration, identify the HTTP client owner and test two distinct users against a simulated cookie-setting service. Inspect outbound cookies, caller-owned client lifetime and protocol-session scope. Confirm the installed build contains the September 15 change before expecting its new default.

Evidence Chain

Receipt 1 / microsoft/agent-framework / commit / Sep 15, 11:59 AM GMT+2 Make HTTP cookie persistence explicit

Internally created clients reject saved response cookies; supplied clients retain behavior and remain caller-owned.

 Receipt 2 / microsoft/agent-framework / docs / 2026-09-15T09:59:35Z MCP ownership and cookie migration

Cookie rejection applies within sessions too, preserves explicit cookies and does not partition protocol sessions or server-side state.

Confidence / strong

Implementation, public migration documentation and synthetic regression assertions agree on the narrow default change. We did not execute the full integration suite.

Limit

The newest listed Python release at reporting time, September 10’s 1.18.0, predates this source change. A synthetic regression is not proof of a real exposure, and rejecting cookies is not complete user isolation.

What would change this

Revise the call if the change is reverted, an affected managed-client path still replays response cookies, or the release adopts a different ownership contract.

Watch next. Watch for a Python release carrying the change and verify both cookie-dependent migrations and two-user protocol-session isolation.
