Today's Action

Test / Project-specific claim
action

Check when the running agent received your correction

What changed. Harness adapters delay durable acknowledgment until their native intake path records the user entry. The web timeline splits folded work around that entry; a temporary pending chip is not a durable receipt.

Why it matters. Teams diagnosing an apparently ignored instruction need to distinguish delivery delay from behavior after the instruction reached the runtime.

Claim coverage / complete 29 / 29

All 29 included projects and all 13 core coding agents have fresh source receipts for this edition.

Teams evaluating the merged QM steering change One focused session per configured harness

Compare correction intake with tool order

In a disposable session, send two identical corrections while work runs. Compare each recorded intake with the next tool calls and reload. Repeat with a run ending before intake; do not treat a vanished pending chip as proof of delivery.

Confidence / developing

Limit

We did not repeat live integrations or verify deployed pins. Intake does not prove obedience or undo prior tool effects. Pending browser state clears on run end or reload.

What would change this

Revise the call if authenticated runs show intake entries appearing before the corresponding native event or live/reloaded ordering disagreeing.
